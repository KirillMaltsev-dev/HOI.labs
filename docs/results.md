**Сравнение реализаций**

Windows, Java 21.0.7, 100 строк, seed 42, каждый замер по 3000 мс, задержки внутри шага и между шагами по 10 мс, 3 повтора

Перед каждым запуском создавался новый список из одинаковых данных, порядок запуска реализаций чередовался, ввод и печать во время измерения не выполнялись

**Теоретическая оценка**

Шаг — завершённое сравнение соседней пары с возможной перестановкой, сравнение уже упорядоченной пары тоже считается шагом

Обозначения: p — число потоков, T — время измерения, a — внутренняя задержка, b — задержка между шагами

При n ≥ 2 идеальная верхняя оценка для собственного списка без учёта ожидания блокировок и обходов

```text
Slinked ≲ pT / (a + b)
```

В ArrayList внутренняя задержка выполняется под общим монитором, поэтому при a > 0 добавляется ограничение

```text
Sarray ≲ min(pT / (a + b), T / a)
```

Это асимптотические оценки, а не точное число шагов за короткий интервал, первый шаг не ждёт внешнюю задержку, на границах интервала возможна поправка порядка p

При нулевой сумме задержек конечную оценку нельзя получить только из этих формул, при n < 2 обе реализации делают 0 шагов

В бесконечной сортировке нет конечного общего числа шагов, для p потоков по R полных проходов фиксированного списка отдельная формула проверки счётчиков имеет вид pR(n−1)

**Почему получились такие числа**

У ArrayList одновременно выполняется только один шаг, внешние задержки разных потоков могут перекрываться, поэтому переход от одного потока к четырём дал примерно двукратный прирост, дальнейшее увеличение числа потоков почти ничего не изменило

Связанный список здесь не оказался быстрее, сортировщики начинают проходы рядом и конкурируют за перекрывающиеся тройки узлов, а поиск каждой пары снова идёт от головы и задерживается на занятых узлах, полный проход требует O(n²) переходов против O(n) обращений к парам у ArrayList

Локальные блокировки позволяют работать с непересекающимися участками одновременно, но сами по себе не гарантируют ускорение, оценка pT/(a+b) предполагает отсутствие конфликтов и потому заметно завышает результат этого алгоритма продвижения

Фактические шаги ниже идеальных оценок также из-за ожидания блокировок, обходов и неточности Thread.sleep, по 96 шагам одного потока получается около 31 мс на шаг с двумя задержками вместо идеальных 20 мс, это косвенная оценка общей стоимости шага, а не отдельное измерение точности таймера

Число перестановок у реализаций различается, поскольку потоки проходят пары в разном порядке, сравнение одной пары несколькими потоками увеличивает число шагов, но не обязательно даёт новые перестановки

После каждого запуска проверялось совпадение количества и содержимого записей с исходными данными с учётом повторов, полная сортировка за 3 секунды не требовалась
